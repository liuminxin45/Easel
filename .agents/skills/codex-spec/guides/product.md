# Product outcomes

Start with the job the user wants to accomplish, not the solution you happened to
choose. For each consequential ambiguity distinguish a user requirement, an
existing product convention, a proposed design and a temporary assumption.

For a meaningful feature establish:
- The intended user and entry point.
- Their action, observable feedback and final state.
- Existing behavior to preserve and explicit scope exclusions.
- References that explain what good looks like.
- Unknowns whose answers would change the implementation.

Write acceptance in observable terms. "Three buttons implemented" does not
establish that a reader understands the workflow. A teaching interaction might
instead require the reader to see the model's limitation, add a capability and
observe how the same task changes. New feedback may refine this goal.

Use a small representative prototype for uncertain interaction or appearance.
Choose project conventions when they provide enough direction. Ask the user only
where a consequential decision cannot be inferred; make useful independent
progress while waiting. There is no mandatory design approval stage.

When feedback arrives, distinguish:
- Implementation violates a confirmed criterion: repair the defect.
- The chosen design meets the text but fails the user's job: revise design and
  acceptance together, rather than polishing the same unsuitable solution.
- The user changes the goal: amend scope and preserve the relevant decision.

Do not convert your proposed solution into an immutable requirement. Keep several
valid implementations possible. Product quality includes comprehensibility,
interaction continuity and useful copy, not just pixel measurements.
