# Easel 私有工作流扩展

## 目标与边界

主工程位于 `D:/Projects/Easel`，基线为本地 fork 的
`514caf8089f89b4793063aeae867690cc69bf8b8`，官方共同基线为
`5a597e5f3ef5b01098b53f36caf719dd9a32b7bf`。
保留该 fork 的自定义 Python 数据源协议，不回退到官方较早的热点实现。

上游继续拥有 `easel/`、原 `web/frontend/src/App.tsx`、标准技能及组件。
私有业务在 `easel_workbench/`，前端在 `web/frontend/src/workbench/`。
前端直接复用上游样式、图标及选择控件；普通 Easel 构建与私有工作台构建分开。
业务迁移必须先保持现有作品、版本、账号、明确交付授权及未知回执合同。
不因引入底座而开放通用模型切换、自动发布、媒体制作或已退役页面。

## 兼容服务

`runtime/` 从当前正式不可变包迁入，不从有未提交更改的旧工作目录批量复制。
导入工具将内部依赖改为包内绝对导入，来源及导入后哈希见 `import-baseline.json`。
它是待逐领域收敛的兼容层，不宣称已经替换为官方 Codex 执行器。
现有冻结输入、原始反馈、原生会话、operation_id 和未知回执不可重建或重放。

## 技能与流程的职责

内容生产是组合技能：写作、配图、独立核验各自保留版本，组合入口不增加模型回合。
选题研究、参考拆解、传播分析和按需经验整理同样通过明确技能执行。
技能方法、正文及资源唯一登记在内容项目的 `.agents/skills/capabilities.json`；
`creator_skill_versions` 是这些方法的冻结发布版本，不是另一份实时文件目录。
画像选择已发布版本或明确试用候选，受理时冻结实际版本和字节。

程序工作流负责把技能连接到可靠的业务操作：接收材料、冻结输入、执行、接收文件、
独立核验，再按决定和授权归档或交付。作品、版本、反馈、账号凭据、幂等事务、
队列及未知回执属于业务服务。这些状态不能变成模型自行解释的技能文字。
Python 数据采集沿用 fork 的自定义来源协议；抓取、去重、入库仍由程序完成，
需要模型的新闻增强才绑定选题研究技能。

可读制作方案和创作方案资源是本次技能输入；执行步骤和模型回执是运行记录。
它们都不建立一套平行的可发布技能注册。

| 边界 | 实现与责任 |
|---|---|
| 技能任务策略 | `easel_workbench/skills.py`，纯数据规则；从已登记任务范围派生启动动作，不访问数据库、网络或模型 |
| 技能与画像版本 | `runtime/creator_runtime.py`，冻结发布包、候选、画像固定版本；新受理校验任务适用范围 |
| 实际执行 | `runtime/task_runtime.py`，准确输入、技能快照与步骤/模型回执；组合入口和实际模型子技能分别记录 |
| 业务操作 | 作品、反馈、账号与发布服务负责本地事务和明确授权；不由技能正文自行操作台账 |
| 前端 | 私有UI消费服务端动作与任务策略，绑定当前所看版本、画像和明确试用；不按技能ID另写一套分发逻辑 |

参考拆解、经验整理和发布复盘共用显式执行选择合同：`creator.profile_id`、
`profile_revision`、`skills` 和 `trial`。待改善技能是整理经验的材料，
实际执行者仍是经验整理技能。已受理复盘在内部传递并核对同一份冻结快照；
中途失败后发布候选或修改默认版本，不得改写原请求的试用身份与输入。

## 维护方向

上游工程、私有业务服务、技能方法与前端呈现分别维护。新增制作方法先进入技能候选，
复用已有作品/执行服务；只有新的确定性能力、持久业务实体或外部协议才增加代码服务。
不为每个技能增加页面、执行器、导航入口或后台进程。

`runtime/` 继续保留迁入合同；逐领域改动时收敛相应服务，不靠移动全部文件制造一层新壳。
旧账号检测等退役接口只负责明确返回退役结果；人工桥接和历史凭据仍由账号/发布服务管理。
上游自带技能与原运行时保持独立；私有任务必须经过已选版本冻结及现有授权入口，
不能由扫描当前磁盘文件直接重建历史制作。

## 数据与上线门禁

正式服务与业务数据已迁入Easel，旧服务写入者已停止；实际版本和证据见 STATUS.md。
数据迁移须采用 SQLite backup、一致性检查、文件 SHA 核验和来源记录。
切换必须排空已知在途制作、采集和交付，核对每个进程身份，确保只有一组写入者。
回退需要保留切换后产生的业务状态，不能恢复旧库或重新发送未知任务。
浏览器继续使用原 HTTPS origin、草稿键、附件数据库及操作标识。

## 验证

前端 `npm run check:workbench` 使用 TypeScript strict。
`tests/test_workbench_architecture.py` 用 Python/TypeScript AST 及负控检查依赖方向、
上游改动边界、技能策略纯度、采集注册一致性和连接环境隔离。
冻结包缺少明确绝对业务根目录时拒绝启动，防止误建包内影子数据库。
`npm run build:workbench` 在 Node 24.19.0 下生成独立不可变 native 候选。
候选通过不等于已上线。当前正式版本已通过领域合同、实际候选浏览器、数据及故障恢复验收，后续变更仍须绑定准确快照。
