# 对话快速受理与离页执行修复

Spec: [chat-fast-accept](../../specs/chat-fast-accept/spec.md)

## 问题与改动

目标会话 `workbench-ba8f6198e05b4abb8b0640c747e9e9fc` 的原讨论已完成；两份后续贴图方案存在，但没有对应执行回合。旧页面必须先等 `/api/chat/plan`，再请求 `/api/chat/stream`，准备没有独立持久回执。日志中有 43.663 秒的 POST，超过客户端通常 30 秒读取期限；日志的 `/api/other` 分类不能单独证明每条慢请求属于该会话。

新增 `/api/chat/submit`：先原子保存原始输入、请求身份与准备依据，返回 202；服务器应用随后完成原有 plan、prepare 和原生 submit。原生引擎、RPC、作品/调用同事务登记、冻结输入和交付权限保持。页面收到对应回执后清空匹配的输入，在原 ChatPage 消息和活动位置显示“AI已接收，正在处理”。服务器收到和模型最终受理是两个准确阶段，准备失败明确显示并保留输入。

离页、刷新和关闭浏览器不会取消已接收请求；重新进入只读同一任务。丢失接收响应只通过 GET 核对，不再次发送。持久接收阶段也纳入部署空闲检查。准备期间画像、技能默认版本或原始依据变化时明确失败，不静默换用新候选。原来 HTTP 提交入口的本地事务与任务启动也由服务持有，避免客户端取消造成登记后漏启动。历史 unknown 不自动重放，本次没有重发目标会话的两条旧制作方案。
