初始恢复使用后端 `workbench-20261031-170523`（d43b1c48…）与前端
`native-mobile-loop-20261101`（22e19e19…）。随后明确发现 native adapter 在
ASGI loop 直接执行 `BEGIN IMMEDIATE`（原连接超时 20 秒）及同步业务动作，
热点、画像、作品树读取也存在同类问题。这是确定的事件循环阻塞机制；
不能由只有少量并发的页面测试证明不存在。
会话 HTTP 适配器还在主 loop 同步逐条读取会话历史和生成方案；本批同样把这些
明确的同步区段移出 loop，原生 submit/stop/SSE 和用户回答 Future 保留原 loop。

这些同步区段统一交给通用 `easel.web_services.concurrency.run_sync`，在工作线程
执行，原 async 写锁、准确操作 ID 和 pending/unknown 规则保留。请求取消时
等待已启动线程真实退出，再释放调用者的锁，避免第二次操作与第一次重叠。
原 shared planning 的同步读写仍只保留一份实现，异步入口调用线程中的同一逻辑；
选题读改写使用同 context RLock，避免异步化后并发写入覆盖。原 App、CSS和前端
包保持，后端重新冻结，实际选择器和 SHA 记录在本任务 candidate/deployment 证据。

用户后续明确授权直接切换、重启后端。若确有活动制作，先通过已有准确回合
停止协议收敛，保留原始输入、文件和实际回执，再使用原部署准入切换；不绕过
unknown/原生队列准入，不因重启自动再次制作。代码只推自有 origin。

## 最小强化方案

入口继续是 Tailscale + WebToApp/PC 浏览器，不引入消息平台。

1. **系统托管。** 当前同凭据所有者的 Windows 任务持续拉起管理器，角色 OS 锁
   保证单写入者；不依赖 Codex/浏览器窗口存活。异常有日志，重复触发不重复启动。
2. **请求与慢任务隔离。** 网页/鉴权/健康请求保持响应；SQLite 等待、文件扫描、
   耗时同步动作移出 event loop。已有采集、制作、交付 worker 与持久队列继续复用，
   不新增另一套制作引擎或数据库。
3. **准确恢复。** 页面重连只恢复服务器状态；受理的任务及版本持久化，原文件和
   草稿保留。未知回执展示待核对，不自动重放。重启不是把失败伪装成成功。
4. **后续最小增量：独立可用性监督。** 分开记录进程存活、HTTP响应、Tailscale入口
   三层探针；连续失败后按角色恢复，并增加冷却期/熔断防重启风暴。外网断链不能
   当业务进程故障无限重启。本批进程退出自愈已实现，HTTP假死的自动杀进程策略
   未实现，不将上述后续项算作已上线。

不建议现在引入 Kubernetes、第二套工作台或新的消息机器人。当前单机用已有
Windows 托管、原生工作进程、事务与队列即可先把确定的问题收住；持续探针验证
后再扩大自动恢复范围。

边界：现有交互任务依赖原凭据所有者保持 Windows 登录，锁屏可以，注销后不能
运行；主机休眠、关机或公网/Tailscale 断链时，任务本身不能提供可用性。
一分钟触发是检测周期，启动及锁核对仍需要额外时间，不能承诺零中断。
主机的域名探测经过本机 Tailscale 路径，也不等于独立公网线路验收。
用户本次明确反馈 vivo WebToApp「已能打开」，它只确认当次实体入口恢复，
不代表今后持续可用或所有制作操作均通过实体设备验收。
