# 独立健康中控与真实每日验收

过去的可靠性验收偏重 PID、入口可达、重连和受控小数据用例，未持续证明“该采集已经按时完成”和“真实规模下关键入口仍快”。完整业务测试与故障注入还依赖开发回合，不能代替持续运行的检查。本轮将这些结果分开记录，不再以进程存活宣称业务全部正常。

## 运行边界

独立源代码位于 `tools/health-control/`，随自己的 fork 提交，不写官方 upstream。实际环境、不可变控制器版本、状态及 Windows 任务均在 `D:/Services/EaselHealthControl/`，不导入应用模块，不依赖应用 venv 存活。第一次安装实测 LocalAppData 被 Codex 打包进程重定向，故选择实际 D 盘目录供 OS 任务共享；半装任务已核对原始动作后归档迁移。

应用只提供集中端口：`diagnostics/health_bridge.py` 复用原身份、空闲、原生队列、历史未知审计与停写围栏；`canary_export.py` 只读导出最小画像、当前技能/资源和设置凭据引用。真正应用依赖只在受验证冻结版本的独立子进程加载，应用缺失时中控仍能写自己的故障报告。

## 检查与恢复

- `EaselHealthControl` 登录时及每分钟启动，普通观测约50秒；本机/Tailscale nonce、准确版本和进程身份分别核对。新鲜度依据启用源、当前修订与真实日/周/间隔排期，不要求周更源每天有新文章。
- 业务与传输各有结果。提供者500、部分采集、错过排期、正常等待、慢入口不直接转为整机重启。
- 连续3次本机失败、90秒启动宽限、120秒冷却、30分钟最多2次。预算及操作身份先持久化，二次核对 PID 创建时间/版本/空闲/未知回执；仅复用既有 server 恢复或准确 manager OS 任务。
- 恢复中断只允许核对原请求、确认原执行进程已退出后清理对应的自有暂停标记，绝不重放终止操作；不动其他部署暂停。状态损坏/回执未知保留诊断，不通过清状态获得新预算。
- Windows 任务负责中控本身的重启与下一分钟补跑；普通监控有5分钟OS兜底，恢复IPC180秒边界；每日已受理模型工作不因2分钟任务限制被强行杀掉。

## 每日真实样本

`EaselHealthDaily` 默认北京时间09:10，之后每30分钟核对当天原操作。用户已明确授权每日一次真实采集和真实 Agent 制作。实时读取原 HN 源，区分获取时间与文章发布时间；使用当前活动冻结版原 ChatAdmission/ChatBusiness/ChatService/CodexAdapter 在独立数据和输出目录制作一张 PNG。

独立设置修订采用严格 workspace-write，不继承正式 Full access。正式会话、作品、账号/发布授权均不复制；所需冻结资源只导出有限几 MB，不复制约348 MB正式DB。凭据只读引用，禁止明文日志。制作结果须有原生完成回执、准确版本、实际工具活动、可解码非空PNG、尺寸/SHA和操作身份元数据。明确只验收真实 Agent 工具绘图，不能冒称专用 AI 生图工具已经可用。

操作受理身份先落盘，未知只核对不重发；只有确认子进程退出且尚未发送的准备失败，可用同一身份最多准备3次。采集失败即使图片成功也不能显示全绿。样本不采纳、不发布、不自动学习，不进入正式作品库。停机/休眠/凭据用户退出时不能运行，OS在可用后补跑。

## 性能回归与本轮修复

原日志增加请求trace下的实际查询耗时/次数、复制字节/次数、BUSY、写事务占锁；`/_workbench/diagnostics` 为独立只读凭据端口，入口liveness仍小且独立。中控只读有界快照及各存活角色日志尾，能看到后台长事务；不记录SQL、正文、Cookie、凭据或原始异常信息。

遗留 `creative_recipes.preview` 整库克隆已改为同一编译器的 query_only 路径。新建/修改/成稿、贴图/文章、legacy/显式画像均与原克隆oracle深等，包括准确技能、父版、冻结参考、附件、原始意见及批注；正式消费同一preview_id。真实384 MiB SQLite与独立writer验证0次backup，关键HTTP预览禁止数据库复制。

本轮实际观察到 manager 因 `pids.json` 被Windows临时占用，原 `os.replace` 抛PermissionError退出。现在管理心跳复用同一原子发布函数，并对短暂分享冲突有界重试，旧完整记录保留，永久I/O失败不伪装成功；已用真实Windows禁止share-delete的读句柄验证。报告并发写入竞态亦已复现并修复。

上线观测又抓到 learning 进程每轮约1,900次查询，写锁4～18秒。根因是后台领取任务时无条件重建历史投影并重写相同数据。取消后台重复同步，显式手工整理仍走同一源准备；未变化索引不写。600+600条反馈的原实现3024查询，修后15次；407,138,304字节测试库约29ms、写锁约1ms。不是通过禁用角色、改排期或删除数据获得改善。

## 首次真实样本的失败与修复

原样本 `health-20261103-ff7854e632e12958` 已真实采集 HN、调用 Codex 并取得 native completed/hook completed，但没有PNG。Agent明确记录 AppData 底层Python在严格沙箱中无法执行，只保存失败记录和配文。文件验收因此失败；原回合、失败记录和素材保留，不因为原生完成就显示制作成功，也没有再次发送该任务。

已将本机 Python/Pillow/中文字体准备到样本自己的 `.tools`，不携带 venv 重定向、凭据或其他用户包。最终同源码经实际 Codex Windows sandbox（只读根目录、工作区可写、禁网）无模型验证：旧解释器拒绝、工作区工具生成960×1280中文PNG及正确操作身份、工作区外写入被拒绝。此权限探针是工具修复证据，不冒充第二次真实Agent成功样本。每日无人值守仍最多一次原生受理；下一次样本会使用修复后的工具环境。约70MiB工具只在每日隔离准备阶段使用，不进入线上HTTP请求，不复制正式DB。

已完成的恢复操作若只是响应丢失，可按原请求读取持久完成回执解开pending，预算保留；真正未知执行仍不重放。确认还未终止进程的准入/队列变化归为deferred，避免把可证明的未执行误报未知。
