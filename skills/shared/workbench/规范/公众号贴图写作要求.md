# 微信公众号贴图写作要求

依据用户提供的这次贴图创作复盘制定。后续微信公众号贴图默认执行本规范，优先于长文写作 skill 的篇幅、节奏和情绪规则。公众号长文、小红书、短视频不自动套用本规范。

## 先写清一个观点

定位与选题执行[定位与编辑原则](定位与编辑原则.md)，自制主视觉执行[图片规范的具象小猪场景优先](图片制作要求.md#具象小猪场景优先2026-10-23)。本文件只规定贴图适配，不另设文风或免责说明规则。

Tech Pulse 专用标题规则：本栏目标题固定为 `Tech Pulse｜科技脉搏 YYYY-MM-DD`，日期为本期北京时间日期。这是用户2026-10-10指定的栏目例外，不受通用标题20字内部上限约束；首图保留完整标题，其他题材仍执行原上限。历史期标题保持原样。

动笔前先写出“一句话到底想说什么”。整篇围绕一个清楚的信息主线；可为变化、可能性或判断，不硬造观点。图片为主，文字辅助说明；不把长文压缩成贴图，也不为了讲完整而展开多个行业趋势。

先组织图片的阅读顺序，再写高度总结的配文。事件、反差、例子、判断可以作为组织参照，不强制独立封面或多图；允许一张原帖截图加一段解读、HTML 图解、工具实测截图，也允许纯文字内容。每张图承担一个主要信息，不把长文切碎后塞进图片。

张数按内容和阅读密度决定，不把“一张能讲清楚”变成固定一张。原帖消息和操作入口可各用一张；一张过挤时优先拆成多张，内容不足则不凑图。

有图片的贴图，第一张必须显示完整的本篇标题，与交付标题一致，可分行但不能只放一个不同的抽象口号。标题可以和正文、原帖或实测截图放在同一张图，不为此强制增加封面。纯文字内容仍直接给标题。用截图作首图时，在独立标题区加字，保留原始截图原貌。

首图通常承担封面作用，应优先让读者知道主体是谁、发生了什么或提出了什么判断。人物观点或发言题材，姓名及核心判断尽早进入首图视觉重点，姓名可独立醒目署名，不能只靠小字来源识别主题。封面可同时呈现必要内容，后续图片再承担解释；不固定新增一张纯标题页。标题概念须对应原意，分清用户使用水平、实际体验与对AI能力的理解等不同层次。[完整本次指导及措辞确认](../内容/Karpathy谈AI认知差距/用户指导-封面主体与概念措辞-2026-10-12.md)保留；“AI认知差距”曾获局部确认，后因歧义改为明确的人与人之间的理解差距；最终采纳及纠偏见[复盘](../内容/Karpathy谈AI认知差距/创作复盘-版面与标题-v0.6.md)，不成为其他题材的固定标题。

交付贴图配文时，必须单独提供可复制的标题与正文，分别标明“标题”“正文”，按[内容总规格](内容总规格.md#内容完成条件)放入各自代码块。标题与首图及草稿包保持一致，不能因为图上已有标题或包内已有title字段，就省略聊天中的标题。仅补标题时可只交付标题；完整贴图交付须同时给出两部分。[完整用户指导](../内容/腾讯开源TeamAI/反馈.md#2026-10-10标题与正文分别交付)。 修改贴图配文后默认再次交付完整标题与正文，不能仅给局部改句让用户自行拼接。[本次完整反馈](../内容/美国年轻程序员就业与培养断层/反馈.md#2026-10-12修改后交付完整可复制文案)。

每段检查：删掉后核心观点还能成立吗？如果能，优先删除旁支分析；必要的证据、适用条件和来源仍应保留，不能为了短而改变事实。

## 篇幅和图片

| 项目 | 内部标准 |
| --- | --- |
| 标题 | 不超过 20 字，直接、准确、一眼看懂，不做标题党 |
| 正文 | 不超过 1000 字；图片承担主要信息，配文按信息量高度总结 |
| 更短的内容 | 不设最低字数或 700～900 字目标，不为凑字数补内容 |
| 主图 | 优先 3:4 竖图，具体像素在单篇需求中确定 |
| 图片数量 | 不写死；发布时以后台当时可用数量为准 |
| 话题 | 正文配文末尾不添加 #话题 标签 |

1000 字是内部交付上限，不是写作目标。交付前实际计数，不凭目测。作为保守的本地检查，标题和正文按 Unicode 字符计数，计入标点、数字、英文字母、话题和可见链接，去除换行；平台如何计数、可接受的字符及最终限制，以编辑器实际提示为准。字数报告放在交付说明中，不混入正文。

按用户2026-10-09澄清，1000字上限检查的是贴图正文配文，不把图片上的文字加进去。图内文字单独按手机可读性与信息密度检查；公众号文章流水线没有1000字上限，不为满足贴图限制删短文章。

按用户2026-10-09最新指导，标题不做标题党，正文配文末尾不加 #话题 标签。标题直接说明主题、事件或功能，不用夸张、悬念或隐去关键条件换取点击；正文自然结束，不再自动补话题段。[完整原话与调整范围](../资料/风格研究/贴图标题与话题标签指导-2026-10-09.md)保留。2026-10-08默认加标签及此前吸睛标题倾向已撤销，历史稿件不覆盖。

这些数值首先是用户选定的内部标准。用户提供的非官方资料称平台存在标题 20 字、正文 1000 字等限制，本次仅归档，未独立核验，不能标为微信官方确认。3:4 是优先建议，不是唯一允许比例。资料中图片数量有 9 张和 20 张两种说法，原因未核实，不认定为已证实的版本差异。

## 语言和节奏

文风自然、克制，像真实用户陈述自己的观察。可以有情绪，但不要演情绪。具体损失、反差和后果通常比密集的情绪词更有表达力。

- 不密集堆“卧槽”“义父”“赢麻了”等网络梗；自然出现的个别口语不机械禁用。
- 不连续大量碎句，不为了节奏把每句话单独成段；段落以完整意思组织。
- 不频繁反问，不强行升华；「不是……，而是……」句式一律不用（AI 味浓，[用户 2026-10-12 原话](../内容/纸质书正文混入AI提示词/用户指导-不用不是而是句式-2026-10-12.md)）。
- 不把简单观点拆成许多章节，不把同一个意思换几种说法反复讲。
- 不为传播力编造经历、使用时长、失败情况、对话或感受。

简短贴图在事实句中写清人群、时间及比较范围后，不再追加泛化的“不能推断什么”“并非确定预测”等免责句；用准确措辞自然交代事实与判断，避免为保险重复解释。影响核心理解的真实条件仍靠近相关内容，完整因果边界与核查过程保留在档案。[完整本次指导](../内容/美国年轻程序员就业与培养断层/用户指导-贴图删冗余免责-2026-10-12.md)。

配文直接说功能、用途、变化或一个有根据的判断。没有意义的内容宁可不加；删掉复述图片的完整说明、抽象流程、泛化行业趋势和例行总结。遵循[个人风格指导方针](写作要求.md#个人风格指导方针)。

图片不显示“草稿v0.x”“待用户评审”、核查或裁切步骤等制作信息。需要识别素材来源时，“官方示例”“来源：OpenAI”等短注即可；完整截图范围、验证方式和限制保存在来源与核查.md。影响含义的条件不能省略，但不写成长篇自我辩护或反复提醒“非亲测”。

## 产品变化的亲民表达

用户2026-10-14认可同题豆包分析的学习点：[完整认可及澄清](../资料/风格研究/2026-10-14-读者切入点认可与直白标题.md)。把本篇最值得理解或讨论的问题靠前呈现，不让公示流程、参数清单遮住核心意思；标题用明确动作和熟悉对象降低术语成本，优先直接中文消息词。封面先画清主体关系、变化或阻挡来自谁，范围重要时用数量、比例或重复形象直观表达。后续页增加理解，不仅搬核查材料或增加名单。按实际消息选择方法，不固定冲突角度、张数、字体或构图，也不把高阅读推定为某个元素的已证实效果。

工具与产品更新依据实际变化选择合适的切入点，再讲清读者熟悉的工具里发生了什么。体验明显改善的消息，可以聚焦少了一步操作、用起来更顺手、原有麻烦得到解决等具体变化，按事实自然表达振奋；模型名、技术术语与性能数字帮助读者理解，图片也突出这次更新最值得表达的变化。

当更新确实有影响使用选择的重要代价或限制时，再说明相关取舍。例如提速伴随更高额度消耗，比较应在同一产品、模式和基准下进行；API token价格、订阅额度消耗、购买额度费率分别核对，不能用其中一项代替其他使用环境的成本。相关关键材料已经取得时，应在成品里留下足够信息供读者取舍；没有披露的数据不推算、不补造。

“收益、代价、怎么取舍”仅是合适题材的组织方式，不要求每次更新都分析成本、寻找负面条件或回答“该不该用”。没有额外代价的体验改善，直接讲清改善即可；表达重点随主题和材料决定。实际效果有实测才写成亲测，场景举例与助手建议清楚区分。图片和配文继续简洁，不新增实用性选题门槛或大陆可用性检查。

依据用户对GPT-6.1贴图的[两轮完整反馈](../内容/GPT-6.1%20Sol%20ultrafast%20发布，Codex%20steering%20改进为即时响应/反馈.md)：先提出亲民表达，随后明确按实际更新选切入点，不把额度案例固定推广。该篇不重做，旧稿和原件保留。

## 本次经验示例

此前案例仅用于理解当时反馈，不替代下方当前生产要求。

本次素材的核心判断是：“Reset 可以很爽，但稳定、好用、易用，本来就是付费产品应该提供的。”

围绕它，解释额度补偿与时间损失的差别即可。产品战略、Agent 行业复杂度、研发体系等旁支，应在不能直接支撑这个判断时删除。

> 额度可以 Reset，但时间 Reset 不回来。

把“有更新。用户赢。没更新。用户还是赢。”改成更自然的完整表达：

> 有更新，用户得到新功能；没更新，用户得到额度。怎么看，好像都不亏。

标题例子包括“额度能重置，时间不能”“Reset 很爽，但问题还在”“别把补偿当成福利”。这些是本次题材的示例，不作为所有贴图的固定文案。

## 可复用写作指令

> 按微信公众号贴图形式制作。先确定一句话信息主线与图片阅读顺序，再写总结配文。标题不超过 20 字，正文不超过 1000 字，不设字数目标，不凑字数。
>
> 图片与配文服务于一个信息主线，每张图承担一个主要信息，不机械拆成五个章节。不展开无助于主线的行业趋势、产品战略和宏大分析。
>
> 语言自然克制，有情绪但不演情绪。避免密集网络梗、连续碎句、频繁反问、对照句堆叠、强行升华和同义重复。段落按完整意思组织。
>
> 只写有依据的事实和得到确认的经历，保留必要的条件与来源。交付前实际统计标题与正文长度，绝不超过 1000 字；在正文之外报告字数与待核验信息。

## 编辑角度与生产入口

以主题、用户想表达的观点和现有材料为主。读者及阅读理由统一执行[定位与编辑原则](定位与编辑原则.md)，按题材选择变化、体验或思考，不设必答问卷或实用性选题门槛。“中国大陆”仅作作者背景，不开展大陆可用性检查，不据访问、账号、支付、语言、设备或操作门槛筛选内容。

在项目聊天中说“做贴图：主题”，可附观点、真实经历与链接。只有主题时，助手选一个暂定角度完成草稿，在需求和交付说明中记录选择理由；不把助手的判断当成用户已认可的立场，不补造第一人称经历。

顺序为理解主题 → 确定暂定角度 → 核查或实测 → 编排图片 → 制作与截图 → 总结配文 → 检查归档。编排前先检查直接来源中的现成图片、功能卡片和图解；博主消息先读原帖并保存实际截图用于核查。最终主视觉与细节配图的优先序、素材采用及工具选择统一执行[图片制作要求](图片制作要求.md#官方现成素材与个人表达)，不把取材顺序当成成品顺序。需要展示实际效果时使用真实运行或输出图。事实、原作者的陈述与助手判断分清，判断的力度与依据相称。

工具题材不强制每篇实测。介绍官方明确的功能和用途，核查可信直接来源即可；主张实际效果、性能对比、亲测推荐或验证教程时，再完成相应实测并保留记录。未实测不能写成亲测，不用安装、同步成功等过程材料凑图。实测结果只有增加读者理解或判断所需的信息时才进入成品，否则留作内部核查。新闻核查直接来源；博主发言仅证明其作出该陈述，涉及产品正式能力时另外核查直接材料。[完整本轮指导](../内容/腾讯开源TeamAI/反馈.md#2026-10-10实测与内容价值反馈)。

默认聊天触发、本地保存，交付状态为“草稿，待用户评审”。提交、推送、外部发布分别按用户明确指令执行，不启用定时任务。操作入口见 [手动生产流程](../自动化/方案/贴图草稿手动生产流程.md)。

### 已认可的标题与说明做法（2026-10-12）

用户明确采纳本期poster-v02并评价“这版效果很好，记住做法和规则”，本做法成为科技脉搏后续贴图默认；[完整答复](../内容/Tech%20Pulse-2026-10-12/用户答复-采纳-v02.md)、[已采纳范例与前后对照](../内容/Tech%20Pulse-2026-10-12/写法认可与前后对照-v02.md)。这项认可仅覆盖本栏目应用，不把参考站所有写法推广为通用文章模板。

- 标题先让人知道是什么。GitHub和Product Hunt用准确项目／产品名加简短中文定位，Hacker News直接写新闻、文章或研究主题；有依据的原题问句可保留，不为吸引点击加泛化悬念或产品式口号。
